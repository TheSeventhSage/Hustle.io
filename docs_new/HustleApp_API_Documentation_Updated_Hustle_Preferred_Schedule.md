# HustleApp API Documentation

Generated from the uploaded app ZIP, SQL dump, and the upgraded API implementation. The original structure is preserved, but the upgrade requires the migration `database/migrations/2026_05_05_upgrade_uploads_payments_scheduling_tracking_kyc.sql`.

## 1. App Overview

- Runtime: custom PHP 8.1+ API, front controller `index.php`, no external framework.
- Default API base path: `/api/v1`; live base URL: `https://hustleapp.stii.click/api/v1`. Admin API base path: `https://hustleapp.stii.click/api/v1/admin`.
- Database: MySQL/MariaDB using PDO.
- Auth: JWT bearer token issued by `POST /auth/login`; default token lifetime in `config/app.php` is `604800` seconds (7 days) unless `.env` overrides `TOKEN_TTL_SECONDS`.
- Request body: JSON for normal `POST`, `PUT`, and `PATCH` writes. Send `Content-Type: application/json`.
- Upload endpoints use `multipart/form-data`; do **not** send JSON headers for file upload requests.
- Paystack webhooks send raw JSON with `X-Paystack-Signature`; this endpoint is called by Paystack, not directly by the mobile/frontend app.


### Upgrade highlights

The upgraded API adds these mobile/frontend-facing capabilities while keeping the existing route style and response envelope:

| Area | What changed |
|---|---|
| Media uploads | `POST /media/upload` accepts safe images only and creates `media_assets` rows. Use returned `asset.id` in profile/service/portfolio/KYC requests. |
| Media retrieval | `GET /media/{id}/file` streams uploaded images. KYC/private media requires owner/admin bearer token. |
| Booking confirmation | Artisan confirmation now moves a booking to `awaiting_payment`; work does not begin until backend payment verification succeeds. |
| Payments | Client initializes Paystack from backend, Paystack payment is verified from backend, and webhook events are recorded. |
| Wallet escrow | Verified payment creates a pending wallet hold. Client/company completion confirmation releases funds to the artisan wallet. |
| Scheduling | Availability can be global or service-specific, with timezone-aware public slots per service. |
| Tracking | Paid/active booking participants can update/read short-lived live location updates. |
| KYC | KYC is country/provider-aware; Nigeria (`NG`) is the configurable default for testing. |

Response format:

```json
{
  "success": true,
  "message": "Human readable message.",
  "data": {},
  "meta": {}
}
```

Errors use the same envelope with `success: false`. Common status codes: `200`, `201`, `202`, `400`, `401`, `403`, `404`, `409`, `415`, `422`, `429`, `500`.

## 2. Authentication and Postman Setup

### Required headers

| Case | Header |
|---|---|
| JSON writes | `Content-Type: application/json` |
| Multipart uploads | `Content-Type: multipart/form-data` generated by the client/browser; do not manually hardcode the boundary. |

### Postman login flow

1. Import `HustleApp_Postman_Collection_Full.json` from this answer.
2. Set collection variable `baseUrl` to `https://hustleapp.stii.click/api/v1`. Do not set `baseUrl` to `/api/v1/admin` because the admin requests already append `/admin/...`.
3. Run one of the login requests. The included tests save `clientToken`, `artisanToken`, `companyToken`, or `adminToken`; the latest login also saves `token`.
4. Send role-specific protected requests. A client token cannot call artisan/company/admin-only endpoints, and vice versa.
5. For idempotent routes, keep `X-Idempotency-Key` unique per real attempt. Reusing the same key for the same route and account replays the saved response.

### Auth requirements by route family

| Family | Roles |
|---|---|
| Public auth/discovery | no token |
| Public media retrieval | no token for public profile/listing/portfolio media; bearer token required for private KYC/selfie media |
| Public service availability | no token |
| Paystack webhook | no user token; requires valid Paystack signature |
| Shared profile/chat/notifications/reviews/media upload | `client`, `artisan`, `company` |
| Bookings | create = `client`; accept/reject = `artisan`; list/show/cancel/location read = booking client or artisan |
| Booking payment | initialize/verify = booking `client`; webhook = Paystack only |
| Location tracking | update = booking `artisan`; read = booking `client` or `artisan`; only after payment is approved |
| KYC, services, availability, wallet, portfolio | `artisan` |
| Hustle create | `company` in the original docs; upgraded route currently also permits `client` for the create/list-decision middleware used by this codebase |
| Hustle applications list/decision | company/client owner middleware in current route registration, or `admin` where admin endpoints are used |
| Jobs | list/show = participant; complete/release funds = `client` or `company` owner only |
| Admin | `admin` |

### `POST /media/upload`

Use `multipart/form-data`, not JSON.

| Form field | Value |
|---|---|
| `asset_type` | `profile_image`, `listing_image`, `portfolio_image`, `kyc_document`, or `selfie` |
| `image` or `file` | JPG/JPEG/PNG/WebP file, max 5 MB by default |

Example successful response:

```json
{
  "success": true,
  "message": "Image uploaded.",
  "data": {
    "asset": {
      "id": 12,
      "asset_type": "listing_image",
      "file_name": "random-file-name.jpg",
      "mime_type": "image/jpeg",
      "file_size_bytes": 245001,
      "url": "https://hustleapp.stii.click/api/v1/media/12/file",
      "uploaded_at": "2026-05-05 08:30:00"
    }
  }
}
```

## 5. Recommended Postman Test Flows

### Public smoke test

1. `GET /health`
2. `GET /categories`
3. `GET /cities?country_id=1`
4. `GET /services?category_id=1&city_id=1`
5. `GET /services/{id}/availability?start_date=2026-05-10&end_date=2026-05-17&timezone_name=Africa/Lagos`
6. `GET /media/{id}/file` for a public uploaded image.

### Image upload flow

1. Login as `client@example.com`, `artisan@example.com`, or `company@example.com`.
2. Call `POST /media/upload` with `multipart/form-data`.
3. Save `data.asset.id` and `data.asset.url`.
4. Use the asset ID in one of these fields:
   - `profile_image_asset_id` for `/profile`
   - `primary_image_asset_id` for `/my/services`
   - `image_asset_id` for `/portfolio`
   - `document_media_asset_id` or `selfie_media_asset_id` for `/kyc/submissions`
5. Display the returned `asset.url` or the later profile/service/portfolio `image_url` response.

### Direct conversation flow

1. Login as `client@example.com`, `artisan@example.com`, or `company@example.com`.
2. Call `POST /conversations/initiate` with `participant_account_id` and an idempotency key.
3. Save the returned `conversation.id`.
4. Call `POST /conversations/{id}/messages` using the saved conversation id.
5. Call `GET /conversations/{id}` to confirm the message appears and the conversation marks messages as read.

### Client booking + Paystack payment flow

1. Login as `client@example.com` and use `clientToken`.
2. `GET /services` to choose `provider_service_id`.
3. Optional but recommended: `GET /services/{id}/availability` using the client's browser/device timezone.
4. `POST /bookings` with selected `scheduled_start_at`, `timezone_name`, destination address, latitude, and longitude. Save `booking_id`, `job_id`, `conversation_id`.
5. Login as `artisan@example.com` and call `POST /bookings/{id}/confirm`.
6. Booking status becomes `awaiting_payment`; notify/show the payment button to the client.
7. Login again/use client token and call `POST /bookings/{id}/payment/initialize`.
8. Open the returned Paystack `authorization_url` or use `access_code` with the payment SDK.
9. After Paystack callback, call `POST /payments/{reference}/verify` from the client app.
10. Confirm booking status is `paid` and job status is `in_progress` through `GET /bookings/{id}` or `GET /jobs/{id}`.
11. When the work is finished, the client calls `POST /jobs/{id}/complete`; this releases the artisan wallet hold to available balance.

### Location tracking flow

1. Complete the booking payment flow until payment is approved and the booking is `paid`/active.
2. Artisan app requests device location permission.
3. Artisan app posts coordinates periodically to `POST /bookings/{id}/location`.
4. Client app polls `GET /bookings/{id}/location` and renders `latest_location` plus `booking.client_destination` on the configured map provider.
5. Stop posting location when the booking is completed/cancelled or no longer active.

### Artisan provider and KYC flow

1. Login as `artisan@example.com`.
2. Upload KYC images with `POST /media/upload` using `asset_type=kyc_document` and `asset_type=selfie`, or submit multipart files directly through KYC.
3. `POST /kyc/submissions` with `country_iso2=NG` for test/default Nigeria KYC.
4. Admin reviews KYC if provider mode is manual; `GET /kyc/status` should show latest status.
5. Upload listing image with `POST /media/upload` using `asset_type=listing_image`.
6. `POST /my/services` with `primary_image_asset_id`, then `GET /my/services`.
7. Add `POST /availability/rules` and `POST /availability/exceptions`, optionally scoped to the service with `provider_service_id`.
8. After completed paid jobs, test `GET /wallet`, `POST /wallet/withdrawals`, then OTP verification. Withdrawal requires approved KYC.

### Company hustle flow

1. Login as `company@example.com`.
2. `POST /hustles`.
3. Login as artisan and apply with `POST /hustles/{id}/applications`.
4. Login as company and call `GET /hustles/{id}/applications`.
5. Call `POST /hustles/{id}/applications/{applicationId}/decision` with `accepted` to create a job.
6. Company/client completion confirmation uses `POST /jobs/{id}/complete` after payment approval where payment applies.

### Admin review flow

1. Login as `admin@example.com`.
2. `GET /admin/dashboard`.
3. `GET /admin/accounts?account_type=artisan&status=active`.
4. `POST /admin/kyc/{id}/review` or `PATCH /admin/kyc/{id}/decision`.
5. `GET /admin/payouts`; then `POST /admin/payouts/{id}/process`.

### Paystack webhook test flow

1. Configure `PAYSTACK_SECRET_KEY` and Paystack webhook URL to `https://hustleapp.stii.click/api/v1/payments/webhooks/paystack`.
2. Initialize payment from the backend using `POST /bookings/{id}/payment/initialize`.
3. Complete payment in Paystack test checkout.
4. Paystack sends `charge.success` to the webhook.
5. The backend verifies the reference again before approving payment and updating booking/job/wallet state.
6. Inspect `payment_events` to audit initialize, webhook, and verify responses.

### Key database relationships used by the API

- `accounts.account_type` drives route access: `client`, `artisan`, `company`, `admin`.
- `media_assets.owner_account_id` controls ownership of uploaded files; private KYC/selfie assets are only readable by the owner or admin.
- `provider_services.primary_image_asset_id`, `portfolio_items.image_asset_id`, `user_profiles.profile_image_asset_id`, and `company_profiles.profile_image_asset_id` point to `media_assets`.
- `provider_services.artisan_account_id` links artisan listings to the owning artisan.
- `bookings` create related `jobs`, `job_financials`, `payments`, and `conversations`.
- `bookings.latitude` and `bookings.longitude` store the client destination for service visits; `booking_location_updates` stores short-lived artisan live coordinates for paid/active bookings.
- `artisan_availability_rules` and `artisan_availability_exceptions` can be general to the artisan or scoped to `provider_service_id`.
- `payments.payment_gateway_reference` stores the Paystack/backend reference; `payment_events` stores initialization, verification, and webhook audit payloads.
- Verified booking payments update `payments.status=approved`, `bookings.status=paid`, `jobs.status=in_progress`, and create a pending wallet `hold` entry.
- Client/company completion confirmation creates a wallet `release` entry and moves provider net funds from pending to available.
- `hustle_posts` are owned by company accounts; accepted `hustle_applications` create `jobs`.
- `wallets` and `wallet_entries` are artisan-only financial ledgers; `withdrawal_requests` use OTP before approval and require approved KYC.
- `kyc_submissions.country_id` and provider fields support country-based KYC configuration; `kyc_submission_files` links KYC images to `media_assets`.
- `notifications` are created by booking, messaging, KYC, hustle, payment, job, and wallet workflows.

## 7. Developer Notes / Current Behavior

- Apply `database/migrations/2026_05_05_upgrade_uploads_payments_scheduling_tracking_kyc.sql` before using the upgraded endpoints.
- Uploads are now supported through `POST /media/upload` and selected KYC/certification multipart paths.
- Uploaded files are stored under controlled storage directories; the database stores only file path/URL metadata in `media_assets`.
- Allowed upload image formats are only JPG, JPEG, PNG, and WebP. MIME type, extension, image validity, file size, random filename generation, and controlled path checks are enforced server-side.
- Default upload limit is `UPLOAD_MAX_IMAGE_BYTES=5242880` bytes unless `.env` overrides it.
- For frontend/mobile image flows, upload first and save the returned asset ID. Prefer asset ID fields over raw URL fields.
- KYC/private media is not publicly readable unless the request includes a bearer token for the owner or an admin.
- Payment must be initialized from the backend through `POST /bookings/{id}/payment/initialize`.
- Frontend/mobile must never mark a booking as paid from Paystack frontend status alone. Always call `POST /payments/{reference}/verify`; the webhook also verifies server-side.
- Paystack webhook URL should be configured as `/api/v1/payments/webhooks/paystack` and requires a valid `X-Paystack-Signature`.
- Booking status flow for service requests is now: `pending` → artisan `awaiting_payment` after confirm → `paid` after backend payment verification → `completed` after client/company completion confirmation. Rejection/cancellation/dispute states are separate exits.
- `POST /jobs/{id}/complete` now releases funds only when the actor is the client/company owner and payment is approved.
- `POST /wallet/withdrawals` requires the artisan's latest KYC submission to be `approved`.
- Availability rules/exceptions accept optional `provider_service_id`; omit it for general availability.
- Service availability responses return UTC `start`/`end` plus display-time values in the requested `timezone_name`.
- Location tracking is near-real-time polling, not WebSocket. Artisan apps should post while a booking is paid/active; client apps can poll for the latest location.
- Map rendering is handled by frontend/mobile using `maps.provider` and `maps.browser_api_key` returned by the tracking endpoint or configured in the app.
- `POST /auth/register` only allows `client`, `artisan`, and `company`; admin users must be seeded/managed separately.
- Auth middleware allows accounts with status `active` or `pending_verification`; suspended/disabled accounts are rejected.
- `X-Idempotency-Key` is supported only on selected POST routes registered with the idempotency middleware.
- Rate limits are file-based per IP per minute: public/auth/private buckets from `config/security.php`.
- Use `POST /conversations/initiate` before `POST /conversations/{id}/messages` when the frontend does not already have a `conversation_id`.

## 9. Frontend/Mobile Implementation Checklist

- Use `multipart/form-data` for file uploads and normal JSON for all other writes.
- Upload profile/listing/portfolio/KYC images first, then attach returned media asset IDs to the relevant create/update request.
- Display images through `asset.url`, `image_url`, or `profile_image_url` fields.
- Capture browser/device timezone using `Intl.DateTimeFormat().resolvedOptions().timeZone` on web, or the mobile platform timezone API.
- Pass the user's timezone when requesting availability and creating scheduled bookings.
- Show the client payment button only after artisan confirmation returns `awaiting_payment`.
- Open Paystack using backend-returned `authorization_url` or `access_code`.
- After Paystack redirect/callback, call backend payment verification before showing paid/active state.
- Request location permission only for active paid booking visits.
- Ensure only booking participants can view tracking UI.
- Poll `GET /bookings/{id}/location` for map updates until a WebSocket layer is added later.
- Do not show KYC documents to normal users; only the owner/admin should retrieve those private media URLs.


## Hustle Preferred Schedule Update

The `hustle_posts` table now supports a preferred schedule window for company-created hustles:

| Field | Format | Notes |
|---|---|---|
| `preferred_date` | `YYYY-MM-DD` | Optional preferred work date. |
| `preferred_start_time` | `HH:MM` or `HH:MM:SS` | Optional preferred start time. Must be sent with `preferred_end_time`. |
| `preferred_end_time` | `HH:MM` or `HH:MM:SS` | Optional preferred end time. Must be later than `preferred_start_time`. |
| `timezone_name` | IANA timezone | Example: `Africa/Lagos`. |

`GET /hustles` can now filter by `preferred_date`, `date_from`, and `date_to`. `POST /hustles/{id}/applications` keeps the same request body but returns `hustle_post_schedule` in the response so artisan apps can display the company/client requested date and time window.
